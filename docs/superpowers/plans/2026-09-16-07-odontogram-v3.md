# Odontogram V3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the legacy scalar/JSON odontogram with a canonical typed dental model supporting multiple findings/treatments, bridges, implant components, removable prostheses, orthodontics, pediatric dentistry, periodontal measurements and history.

**Architecture:** Store current materialized dental state in normalized entities and record append-only odontogram events for history. Prosthetic structures are first-class multi-tooth entities. Voice, clinical plan and UI all use the same domain commands.

**Spec:** `docs/superpowers/specs/2026-09-16-denty-production-platform-design.md`

---

### Task 1: Define canonical dental entities

Add:

```text
Odontogram
ToothFinding
SurfaceFinding
DentalComponent
ProstheticStructure
ProstheticUnit
OrthodonticAppliance
PeriodontalExam
PeriodontalSiteMeasurement
OdontogramEvent
```

`ToothFinding` and `SurfaceFinding` are rows, not one scalar status, so caries and an existing restoration can coexist when clinically recorded.

`DentalComponent.type` includes:

```text
ENDO
POST
CROWN
IMPLANT
ABUTMENT
CORE
VENEER
```

- [ ] Port V5 multi-treatment tests.
- [ ] Test multiple component families on one tooth.
- [ ] Commit.

### Task 2: Implement command reducer

Domain commands:

```text
AddToothFinding
RemoveToothFinding
AddSurfaceFinding
RemoveSurfaceFinding
AddComponent
UpdateComponentState
CreateProstheticStructure
UpdateProstheticStructure
RecordPeriodontalExam
```

Every command updates current state and writes `OdontogramEvent` in one transaction.

- [ ] Reducer tests.
- [ ] Verify event replay reaches same materialized state.
- [ ] Commit.

### Task 3: Multi-unit bridge model

`ProstheticStructure.type = FIXED_BRIDGE`.

Units:

```text
toothCode
role: ABUTMENT | PONTIC | IMPLANT_ABUTMENT
```

Voice phrase “puente 21-23 con 22 ausente” resolves to one bridge structure, not three unrelated tooth flags.

- [ ] Tests for 21 abutment, 22 pontic, 23 abutment.
- [ ] Test replace/repeat bridge creates rework link rather than overwriting history.
- [ ] Commit.

### Task 4: Implant stack

Model linked:

```text

abutment
crown/prosthesis
```

Each can have state and dates while belonging to one treatment/prosthetic chain.

- [ ] Test implant + abutment + crown coexist and render.

```text
REMOVABLE_PARTIAL
```

```text
suppuration
```

Keep multiple exams so UI can compare dates.

Create query:


Use events + periodic snapshots if replay becomes expensive.

UI supports “Ahora / fecha anterior” and highlights added/resolved findings.

### Task 9: Native SVG odontogram UI

Migrate current validated visual semantics:

- green healthy,
- blue correct,
- blue with red border unsatisfactory,
- red pending/caries/indicated.

This clinical color system is separate from menu color restrictions.

Render components independently so endo + post + crown remain visible.

- [ ] Visual/component tests for combinations.
- [ ] Commit.

### Task 10: Voice and plan integration

Voice emits canonical odontogram commands. Treatment plan subscribes to explicit indication records and creates/updates linked plan items through stable source IDs.

- [ ] Integration test: “hay que hacer endodoncia 22 y corona” creates two findings/components and two linked plan items.
- [ ] Commit.

## Acceptance criteria

- No whole-tooth treatment is lost because another treatment is added.
- Bridges are first-class structures.
- Implant components are related, not flattened.
- Periodontal exams are historical.
- Voice/UI/plan share the same command model.
- Legacy odontogram import preserves V11 states.
